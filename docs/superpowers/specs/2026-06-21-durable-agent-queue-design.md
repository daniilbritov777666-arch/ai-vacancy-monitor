# Durable Agent Queue Design

## Цель

Убрать AI-обработку заказов из синхронного цикла мониторинга. Поиск новых проектов должен завершаться и сохранять состояние источников независимо от задержек, временных ошибок или недоступности OpenAI-compatible API.

## Выбранный подход

Использовать локальную SQLite-очередь с узким Python-интерфейсом. Для текущего единственного LaunchAgent-worker SQLite дает транзакционные claim/lease и уникальность заданий без отдельного сервера. Интерфейс очереди не должен зависеть от SQLite-специфичных типов, чтобы позднее можно было заменить реализацию на PostgreSQL.

JSON-файлы в `orders/<order_id>/` остаются главным состоянием заказа и человекочитаемым журналом артефактов. SQLite хранит только планирование и историю выполнения фоновых заданий.

## Компоненты

### `AgentJobQueue`

Новый модуль `vacancy_monitor.job_queue` управляет БД `orders/agent_jobs.sqlite3`.

Таблица `jobs` содержит:

- `job_id` — UUID;
- `order_id` — идентификатор локального заказа;
- `kind` — первоначально только `advance_order`;
- `payload_json` — версия и дополнительные параметры задания;
- `idempotency_key` — уникальный ключ вида `advance_order:<order_id>`;
- `status` — `pending`, `leased`, `succeeded` или `dead`;
- `attempts`, `max_attempts`;
- `available_at`, `lease_until` в UTC;
- `last_error_type`, `last_error_message`;
- `created_at`, `updated_at`, `completed_at`.

Основные операции:

- `enqueue(...)` атомарно создает задание или возвращает существующее по `idempotency_key`;
- `claim_next(...)` транзакционно резервирует одно доступное задание;
- `complete(job_id)` переводит арендованное задание в `succeeded`;
- `retry(job_id, error)` возвращает его в `pending` с экспоненциальной задержкой;
- `fail(job_id, error)` переводит исчерпавшее попытки задание в `dead`;
- `release_expired_leases()` восстанавливает задания после аварийного завершения процесса.

### Producer

`run_monitor` и фильтры остаются без изменений. Callback `on_match` создает папку и состояние заказа, но не вызывает LLM. После сохранения заказа producer ставит `advance_order`.

При старте каждого цикла reconciler просматривает заказы в `awaiting_response_approval`, для которых задание отсутствует, и идемпотентно добавляет их в очередь. Задания в `dead` автоматически не воскрешаются. Это покрывает миграцию существующих заказов и восстановление после сбоя между сохранением заказа и enqueue.

### Worker

После быстрого мониторинга тот же LaunchAgent выполняет ограниченное число заданий за цикл. По умолчанию `AGENT_JOBS_PER_CYCLE=3`.

Обработчик `advance_order` загружает актуальный `state.json` и вызывает существующий autopilot-контур. Если статус заказа уже не `awaiting_response_approval`, задание успешно завершается без повторного действия.

Повторяются только временные сбои: timeout, connection error, HTTP `408`, `429` и `5xx`. Ошибки контракта, валидации, отсутствующие обязательные настройки и отклонение safety-фильтром не повторяются.

Задержки между четырьмя попытками: 1, 5 и 15 минут с небольшим детерминированным jitter. Lease по умолчанию 10 минут.

## Идемпотентность

Уникальный `idempotency_key` предотвращает два активных задания одного типа для заказа. Перед любым внешним действием существующие проверки статуса заказа и sent-файлы остаются обязательными.

Успешная отправка отклика сначала фиксируется существующим способом в `state.json`; повторно запущенный job видит продвинутый статус и завершается без отправки. Очередь не заменяет доменную идемпотентность, а дополняет ее.

## Ошибки и наблюдаемость

Каждая попытка записывается в `orders/<order_id>/jobs/<job_id>.json` атомарно. Файл содержит вид задания, номер попытки, времена, итог и безопасное описание ошибки без секретов или полного ответа внешнего API.

После перехода в `dead` агент один раз уведомляет Telegram и создает `orders/<order_id>/jobs/dead.json`. Временные ошибки до исчерпания попыток не создают Telegram-спам.

Сводный файл `orders/reports/job_queue_health.json` содержит количества по статусам, возраст старейшего pending job, число восстановленных lease и последнюю окончательную ошибку.

## Конфигурация

- `AGENT_QUEUE_ENABLED` — по умолчанию включено при `AUTO_MODE=autopilot`;
- `AGENT_QUEUE_PATH` — по умолчанию `orders/agent_jobs.sqlite3`;
- `AGENT_JOBS_PER_CYCLE` — по умолчанию `3`;
- `AGENT_JOB_MAX_ATTEMPTS` — по умолчанию `4`, диапазон `1..8`;
- `AGENT_JOB_LEASE_SECONDS` — по умолчанию `600`.

При `AGENT_QUEUE_ENABLED=false` сохраняется текущая синхронная обработка для диагностики и обратной совместимости.

## Тестирование

Модульные тесты покрывают схему, идемпотентный enqueue, конкурентный claim, lease recovery, retry/backoff и dead-letter. Интеграционные тесты доказывают, что медленный или падающий AI-клиент не блокирует сохранение новых постов, а успешный worker продвигает заказ ровно один раз.

Полная проверка включает текущий pytest-набор, `compileall`, `git diff --check`, тест восстановления после принудительного завершения worker и live-перезапуск LaunchAgent с проверкой `job_queue_health.json`.

## Не входит в этот слой

- FastAPI, PostgreSQL, Qdrant и Docker;
- несколько параллельных worker-процессов;
- перенос всей машины статусов в графовый фреймворк;
- автоматическое создание SMTP-аккаунта или биржевых учетных записей.

Эти изменения выполняются последующими слоями после стабилизации локальной очереди.
